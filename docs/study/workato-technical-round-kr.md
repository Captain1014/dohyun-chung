## Q3. End-to-end 통합을 처음부터 끝까지 설명해 주세요.

*(Sales Platform 버전 — 기술 깊이 보여주기)*

> "현재 SAP 온프레미스 와 세일즈 플랫폼을 연결하는 통합을 설계,개발,운영하고 있습니다. SAP, aws S3, UPS API, Power BI 등 6개 이상의 시스템이 연결되어 있는 회사 내 가장 큰 플랫폼입니다. **이 플랫폼은 미국과 유럽의 세일즈 팀이 주문, 고객 정보, 제품 데이터를 관리하는 데에도 쓰이며, 300명 이상의 내부 사용자가 매일 사용합니다.**
>
> SAP에서 세일즈 플랫폼 방향으로의 데이터는 IDoc 을 통해서 이동합니다. 고객, 상품, 주문 데이터가 변경되면 SAP이 세일즈 플랫폼 REST 엔드포인트로 전송됩니다. 반대 방향은 PyRFC 폴링입니다. 주문 제출이나 배송 추적 같은 조회는 SAP RFC 함수를 직접 호출하여 개발하고 있습니다.
>
> 문제를 겪은 적이 있었나요?
>
> 1. **근본 원인**: Carrier tracking 크론의 배치 한도가 20,000건으로 설정되어있다는 것을 발견했고, 수십 년간 20000건이 큐에 쌓이지 않아 문제가 발견되지 않았으나 최근 20000 건 이상 누적되어 크론 1회 실행에 45분 이상이 걸렸고, 다음 크론이 이전 실행이 끝나기 전에 시작되며 무한 중첩이 발생했다는 것을 씨퀄 을 이용한 로그 분석을 통해 밝혀냈다.
> 2. **연쇄 장애**: 여러 worker가 동시에 같은 picking을 업데이트하려다 SerializationFailure(concurrent update) 에러가 발생했고, 코드에 savepoint/rollback 처리가 없어 에러 하나가 전체 배치를 kill했다.
> 3. **결과**: 배치가 반복 실패하며 처리 안 된 picking이 계속 누적됐고, cron worker가 포화 상태가 되면서 서비스 전체가 다운됐다.
> 4. 대처: 코드에 savepoint/rollback 추가, 크론잡을 오래된 것 -> 최신 것부터, 리밋 줄이기, 모니터링 자동화 봇 만들기.

## Q6. Workato Recipe가 어떻게 동작하나요?

> "Recipe는 Workato의 기본 자동화 단위입니다. 항상 Trigger로 시작합니다. Salesforce에 새 거래가 생긴다거나, 정해진 시간에 실행된다거나 — 어떤 이벤트가 발생했을 때 Recipe를 시작시키는 역할입니다. 그 다음부터는 Action들이 순서대로 실행됩니다. 데이터를 쓰거나, Slack 메시지를 보내거나, 데이터를 변환하거나 합니다. 조건 분기, 반복문, 에러 처리도 넣을 수 있습니다.
>
> 구조가 직관적이라서 개발자가 아닌 사람도 보고 이해할 수 있다는 점이 인상 깊었습니다."

## Q7. Real-time Trigger와 Scheduled Trigger의 차이는 무엇인가요?

> "둘의 차이는 실행 방식입니다. Real-time Trigger는 이벤트가 발생하는 순간 즉시 실행됩니다. 소스 시스템이 Webhook으로 알림을 보내면 바로 Recipe가 시작됩니다. Scheduled Trigger는 제가 정한 주기마다 소스 시스템에 '변경된 게 있나요?'라고 폴링하는 방식입니다.
>
> 선택 기준은 시스템과 사용 목적에 따라 다릅니다. 주문 처리나 알림처럼 시간이 민감한 프로세스는 Real-time이 맞습니다. SAP처럼 레거시 시스템이 Webhook을 지원하지 않거나, 야간 배치 싱크처럼 실시간이 불필요한 경우에는 Scheduled를 씁니다. 저는 가능하면 Real-time을 먼저 검토하고, 소스 시스템이 지원하지 않을 때만 Scheduled로 내려갑니다."

---

## Q8. Workato와 Zapier, MuleSoft의 차이는 무엇인가요?

> "세 제품이 각각 다른 시장을 타겟합니다. Zapier는 간단한 1:1 자동화에 최적화되어 있습니다. 빠르게 만들 수 있지만, 복잡한 비즈니스 로직이나 규모가 커지면 한계가 빠르게 옵니다. MuleSoft는 완전한 엔터프라이즈 플랫폼이지만 전담 엔지니어링팀이 필요하고 도입 비용이 높습니다.
>
> Workato는 그 중간에서 가장 좋은 포지션을 차지하고 있습니다. 엔터프라이즈 수준의 보안과 거버넌스를 갖추면서도, 비개발자가 직접 Recipe를 만들고 운영할 수 있는 구조입니다. Gartner Magic Quadrant iPaaS에서 7년 연속 1위(7x Leader)가 이를 증명합니다. 고객사 17,000개 이상, 커넥터 8,600개 이상, 누적 자동화 실행 1,500억 건 이상입니다."

---

## Q9. Workato에서 에러 처리는 어떻게 하나요?

> "Workato는 Recipe 레벨에서 에러 처리가 내장되어 있습니다. 실패한 job을 잡아서 재시도, 알림 발송, fallback 동작으로 분기하는 것을 Recipe 안에서 직접 설계할 수 있습니다.
>
> 프로덕션에서 제가 반드시 넣는 패턴이 있습니다. 각 외부 API 호출 단계에 에러 핸들러를 붙여서 실패가 생기면 즉시 알림이 오게 합니다. API 호출이 실패했을 때 아무 소리 없이 데이터가 누락되는 상황은 절대 있어서는 안 됩니다. 특히 SAP처럼 downstream 영향이 큰 시스템과 연결할 때는 더욱 중요합니다."

---

## Q10. Recipe Function은 언제 쓰나요?

> "Recipe Function은 재사용 가능한 서브 Recipe입니다. 코드로 치면 helper function입니다. 같은 로직을 여러 Recipe에 반복해서 넣는 대신, 한 번 정의해두고 필요한 곳에서 불러 씁니다. 하나를 수정하면 그것을 호출하는 모든 Recipe에 반영됩니다.
>
> 실무에서는 데이터 변환, 공통 조회 로직, 알림 패턴이 여러 워크플로우에서 반복될 때 Recipe Function으로 빼는 것이 맞습니다. 예전엔 Callable Recipe라고 불렀는데, 지금은 Recipe Function이 표준 명칭입니다."

## Q11. 고객 온보딩 성공을 어떻게 측정하나요?

> "몇 가지 신호로 봅니다. 첫째, 일정대로 라이브됐는지. 둘째, 프로덕션에서 실제로 쓰이는지 — 테스트 환경에만 머물러 있으면 성공이 아닙니다. 셋째, 고객 팀이 저를 매번 부르지 않고 직접 Recipe를 수정할 수 있는지. 마지막으로 시간 절약, 오류 감소 같은 측정 가능한 비즈니스 결과가 나왔는지입니다.
>
> 기술 구현이 목표가 아닙니다. 실제 사용과 가치 실현이 목표입니다. 아무도 안 쓰는 Recipe는 성공이 아닙니다."

## 개념 정리: 오케스트레이션 레이어가 필요한 이유

> Kwangho의 핵심 메시지: **"뇌(AI 모델)는 있는데, 신경망(연결 인프라)이 없는 상태"**

| 문제                          | 설명                        |
| --------------------------- | ------------------------- |
| **표준 없음 (No Standard)**     | AI마다 연결 방식이 달라 일관된 통합 불가  |
| **보안 없음 (No Security)**     | 중앙 정책 없이 운영, 데이터 유출 위험 상존 |
| **거버넌스 없음 (No Governance)** | 누가 무엇을 했는지 추적·감사 불가       |


> **→ "지금 필요한 것은 더 나은 AI 모델이 아니라, AI가 일할 수 있는 인프라다"** — 신광호

이 세 문제를 동시에 해결하는 표준이 **MCP**이고, 엔터프라이즈 환경에서 이를 구현하는 것이 **Workato Enterprise MCP**입니다.

---

## 개념 정리: MCP란 무엇인가

**MCP = Model Context Protocol.** AI 모델이 기업 시스템에 안전하게 접근하는 표준입니다.

**비유:** USB-C. 연결하는 기기가 달라도 USB C 코드를 통해 연결되듯, MCP는 어떤 AI 모델이든 기업 시스템에 같은 방식으로 연결하는 표준입니다.

**기술적으로 어떻게 동작하나?**
클라이언트-서버 모델입니다. MCP Server가 AI 모델에게 사용 가능한 툴 목록을 노출합니다. 예: `get_deal_by_id`, `list_open_tickets`. AI 모델은 이 목록을 보고 런타임에 어떤 툴을 써야 할지 스스로 결정합니다.

**REST API와 차이:** REST는 호출하는 쪽이 어떤 엔드포인트를 언제 호출할지 미리 하드코딩해야 합니다. MCP는 AI가 목표에 따라 어떤 툴 조합을 쓸지 스스로 결정합니다.

---

## 개념 정리: MCP 3가지 종류


| 비교 항목       | DIY MCP | Application MCP | **Workato Enterprise MCP**    |
| ----------- | ------- | --------------- | ----------------------------- |
| **연결성**     | 단일 앱/수동 | 해당 앱만           | **8,600+ 앱 전사 연결**            |
| **워크플로우**   | 불가      | 단일 앱            | **멀티앱 비즈니스 프로세스 · 엔터프라이즈 스킬** |
| **연결 범위**   | 동일 환경   | 동일 환경           | **On-premise / Private 연결**   |
| **보안/거버넌스** | 구현자 책임  | 앱 수준            | **Trust + RBAC + Audit**      |
| **비개발자 구축** | 불가      | 불가              | **가능 (No-Code)**              |
| **확장성**     | 한정      | 한정              | **자동 확장 (Auto Scaling)**      |


> **"DIY 및 Application MCP는 로컬 문제를 해결합니다. Workato Enterprise MCP는 조직 전체의 과제를 해결합니다."**

**핵심 차이:** Application MCP는 앱 하나를 연결합니다. Workato Enterprise MCP는 "구매 승인 프로세스 전체" — Jira 이슈 생성 + Slack 알림 + Coupa 구매 처리 + SAP 전표 생성 — 가 하나의 AI 스킬이 됩니다.

DIY MCP는 개발자가 직접 만든 순간부터 그 개발자에게 의존하게 됩니다. 한 앱 연결하는 건 가능하지만, 여러 시스템에 걸친 비즈니스 프로세스 전체를 커버하려면 개발 리소스가 계속 필요합니다.

가장 큰 문제는 보안입니다. DIY로 만들면 보통 공유 크레덴셜로 돌아갑니다. POC는 통과하는데 보안팀이 프로덕션 승인을 안 해줍니다. 신입사원도 ERP 전체에 접근 가능해지는 구조가 되니까요.

Workato Enterprise MCP는 처음부터 Gateway로 모든 요청을 통제하고, VUA로 요청자 본인 권한만 적용됩니다. 개발자 없이도 비즈니스팀이 직접 스킬을 만들 수 있고, IT는 거버넌스만 관리하면 됩니다."

---

## 개념 정리: Workato Enterprise MCP 구조

**3개 레이어 + VUA:**

**1. MCP Composer** — 비개발자도 업무 프로세스를 MCP 서버로 만드는 도구. 코딩 불필요.

**2. MCP Registry** — 기업 내 모든 MCP 서버를 등록하고 검색하는 카탈로그. 전사적으로 어떤 AI 스킬이 있는지 한 곳에서 볼 수 있습니다.

**3. MCP Gateway** ← 가장 중요. 모든 AI 요청이 통과하는 중앙 게이트웨이. 권한 설정, 접근 범위 제한, 사용량 제어, **PII 개인정보보호**, **실행 보장**, 감사 로그를 담당합니다.

**4. 거버넌스 / 모니터링·감독** — 전사 에이전트 활동을 실시간으로 추적. 섀도우 AI 방지, 컴플라이언스 감사 대응.

**+ Verified User Access (VUA)** — Workato 특허 기술. 공유 토큰이 아니라 직원 개인 권한으로 AI가 시스템에 접근합니다. 인턴은 인턴 권한 범위 내에서만, CFO는 CFO 권한으로. AI가 사람처럼 권한을 갖는 구조입니다.

> **포지셔닝:** Enterprise MCP는 단순한 연결 도구가 아닌 **AI 거버넌스 인프라**입니다.

**중요:** 기존 Workato Recipe가 즉시 MCP 스킬로 노출됩니다 (Recipe → AI). 새로 만들 필요 없이 이미 구축된 자동화가 AI 스킬이 됩니다.

## 개념 정리: Enterprise MCP 실제 워크플로우 예시

**예시 1 — 구매 승인 (Purchase Approval MCP)**

```
AI 요청 → Jira 이슈 생성 → Slack 승인 알림 → Coupa 구매 처리 → SAP 전표 생성
```

단일 AI 요청 하나로 5개 시스템이 순서대로 실행됩니다. VUA로 요청자 본인 권한만 적용됩니다.

**예시 2 — 직원 온보딩 (Employee Onboarding MCP)**


HR 팀이 직접 No-code로 구축. 개발팀 티켓 없이 자동화 가능합니다.

> **핵심:** AI가 "워크플로우 = AI 스킬"을 사람처럼 권한을 준수하며 실행합니다.

> - RBAC 자동 적용: 거버넌스 내장
> - MCP 즉시 노출: Recipe → AI 스킬로 즉시 전환

## 개념 정리: 실제 기업 사례 — Workato 내부

**"AI 라이선스를 줬는데 아무도 안 씁니다"**

Workato가 자사 직원 1,000명에게 Claude, Gemini, OpenAI 라이선스를 지급했습니다. 4개월 후 실제로 쓰는 직원은 200명(20%)뿐이었습니다.

AI 툴이 실제 업무 시스템과 연결되어 있지 않았기 때문입니다. 직원들은 ChatGPT에 업무 맥락을 복붙하고, 결과를 다시 사내 시스템에 옮겨야 했습니다. 불편해서 안 쓴 게 아닙니다. 연결이 안 되어서 쓸 수 없었습니다.

**MCP 연결 후:**
내부 시스템(HR, 영업, 고객지원)을 MCP로 연결하자 사용량이 폭발적으로 늘었습니다.

> **핵심 인사이트:** AI 도입 실패의 원인은 AI 모델 품질이 아닙니다. AI가 실제 업무 데이터에 접근할 수 있는 인프라가 없어서입니다. McKinsey 95% 실패 통계도 같은 맥락입니다.

**면접에서 쓸 수 있는 한 마디:**

> *"Workato 내부 사례가 인상적이었는데, 직원 1,000명에게 AI 라이선스를 줬는데 200명만 썼다가, 내부 시스템을 MCP로 연결하자 사용량이 폭발했다고 합니다. AI 도입은 도구의 문제가 아니라 연결의 문제라는 걸 잘 보여주는 사례라고 생각합니다."*

## Q-개념1. Recipe와 Genie(AI 에이전트)의 차이를 설명해 주세요.

> "핵심 차이는 결정론적이냐, 목표 기반이냐입니다.
>
> Recipe는 Workato의 기본 자동화 단위입니다. Trigger가 발생하면 미리 정의된 Action이 순서대로 실행됩니다. 항상 같은 입력이면 같은 결과가 나옵니다. 예측 가능하고 감사하기 쉽습니다.
>
> Genie는 AI 에이전트입니다. '이 목표를 달성해라'만 주면, 런타임에 어떤 MCP 툴을 어떤 순서로 쓸지 스스로 결정합니다. 복잡하고 동적인 상황에서 유연하게 대응할 수 있습니다.
>
> 중요한 건 둘이 대체 관계가 아니라는 점입니다. Genie가 Recipe를 MCP 스킬로 호출합니다. 안정적인 비즈니스 프로세스는 Recipe로 정의해두고, Genie가 상황에 따라 그 스킬들을 조합해서 실행하는 구조입니다."

## Q-개념2. Enterprise MCP가 그냥 API 연동이랑 뭐가 다른가요? 고객에게 어떻게 설명하시겠어요?

> "기술적으로 설명하면, API 연동은 개발자가 어떤 엔드포인트를 언제 호출할지 미리 하드코딩해야 합니다. MCP는 AI가 목표에 따라 런타임에 어떤 툴 조합을 쓸지 스스로 결정합니다.
>
> 고객에게는 이렇게 설명합니다. API 연동은 SAP과 Salesforce를 '연결'하는 것입니다. Enterprise MCP는 '구매 승인'이라는 비즈니스 행위 전체 — Jira 이슈 생성, Slack 알림, Coupa 처리, SAP 전표 생성 — 를 AI가 하나의 스킬로 실행하는 것입니다.
>
> 그리고 결정적인 차이가 하나 더 있습니다. API 연동에는 거버넌스가 없습니다. Enterprise MCP는 VUA로 요청자 본인 권한 안에서만 AI가 실행되고, 모든 행동이 감사 로그에 남습니다. IT 보안팀이 승인할 수 있는 구조가 처음부터 내장되어 있습니다."

## Q-개념3. AX가 뭔지, Agentic Era랑 어떻게 다른가요?

> "둘은 레이어가 다릅니다.
>
> Agentic Era는 시대적 맥락입니다. AI 에이전트가 실제 비즈니스 업무를 수행할 수 있게 된 지금 이 시기를 말합니다. AX, Agentic Transformation은 그 시대에 기업이 능동적으로 하는 전환 과정입니다. 단순히 AI 툴을 도입하는 게 아니라 업무 프로세스 자체를 에이전트 중심으로 재설계하는 여정입니다.
>
> 비유하자면 Agentic Era는 인터넷이 생긴 시대이고, AX는 그 시대에 기업이 디지털 전환을 하는 것과 같습니다.
>
> Workato가 강조하는 건 이 AX가 지금 대부분의 기업에서 막혀 있다는 점입니다. 업계 조사에서도 95%의 기업이 AI 파일럿은 성공했지만 전사 확산에 실패했다고 나옵니다. AI 모델이 부족해서가 아니라, AI가 실제로 기업 시스템에서 일할 수 있는 인프라가 없어서입니다."

## Q-시나리오1. POC는 성공했는데 보안팀 승인이 안 난다는 고객이 있습니다. TC로서 어떻게 접근하겠어요?

> "이 상황에서 보안팀을 설득하려고 하면 안 됩니다. 먼저 왜 승인이 안 나는지를 정확히 파악하는 게 먼저입니다.
>
> 대부분의 경우 POC는 공유 크레덴셜로 진행됩니다. 특정 계정 하나로 전체 시스템에 접근하는 구조입니다. 보안팀 입장에서는 이걸 전사 롤아웃하면 신입사원도 ERP 전체에 접근 가능해지는 구조로 보입니다. 승인을 못 해주는 게 당연합니다.
>
> 해결책은 VUA입니다. Workato의 Verified User Access를 활용하면, AI가 항상 요청자 본인의 권한 범위 안에서만 실행됩니다. 인사팀 직원은 HR 시스템만, 재무팀은 재무 데이터만 접근합니다. 기존에 회사가 설정한 접근 제어 정책을 그대로 유지하면서 AI를 추가하는 것입니다.
>
> 이걸 보안팀에게 설명할 때는 '새로운 보안 정책을 도입하는 게 아니라, 기존 정책을 AI에도 그대로 적용하는 것'이라는 프레임이 효과적입니다."

## Q-시나리오2. 회사에 에이전트가 100개를 넘었는데 뭘 하는지 모르겠다는 CIO가 있습니다. 어떻게 접근하겠어요?

> "이 고객은 4단계에 있습니다. AI 도입 자체는 성공했지만 거버넌스 인프라가 없는 상태입니다.
>
> 가장 먼저 할 건 현황 파악입니다. 어떤 에이전트가 어떤 시스템에 접근하는지, 민감 데이터가 외부 LLM으로 나가고 있는지, 중복으로 만들어진 에이전트가 있는지를 먼저 가시화해야 합니다. CIO가 가장 두려워하는 건 규제 기관 감사 때 '모른다'고 대답하는 상황입니다.
>
> 그 다음 MCP Gateway를 중심으로 중앙화합니다. 모든 AI 요청이 하나의 게이트웨이를 통과하면 즉시 가시성이 생깁니다. 한 번에 다 이관하는 게 아니라 리스크가 가장 큰 것부터 순서를 잡습니다.
>
> 경영진 보고 측면에서도, Gateway 도입 후에는 'AI가 이번 달 어떤 업무를 얼마나 처리했는지'를 대시보드로 보여줄 수 있습니다. CIO가 임원에게 설명할 수 있는 수단이 생기는 겁니다."

## Q-시나리오3. TC 역할이 AI 시대에 어떻게 바뀐다고 생각하세요?

*(Eugene이 물어볼 가능성 높음)*

> "바뀌는 것과 안 바뀌는 것이 있습니다.
>
> 안 바뀌는 건 핵심입니다. 고객의 비즈니스 프로세스를 이해하고, 맞는 솔루션을 설계하고, 고객 팀이 스스로 운영할 수 있도록 온보딩하는 것 — 이건 그대로입니다.
>
> 바뀌는 건 설계의 범위입니다. Recipe 시대에는 결정론적 플로우를 설계했습니다. 에이전트 시대에는 신뢰 경계를 설계합니다. 에이전트가 어떤 데이터에 접근할 수 있는지, 어떤 액션은 자율적으로 취해도 되는지, 어떤 결정은 사람이 개입해야 하는지. 이건 Recipe 빌딩보다 컨설팅에 더 가깝습니다.

> TC 역할은 줄어드는 게 아니라 더 중요해집니다. 기술이 자율적으로 움직일수록, 그 경계를 올바르게 설계하는 사람이 필요하기 때문입니다."

## Q-기술1. SAP 온프레미스 시스템에 AI 에이전트를 연결할 때 어떻게 설계하겠어요?

> "Kiss Products에서 실제로 다루는 구조입니다.
>
> SAP이 사내망에 있어서 외부에서 직접 접근이 안 됩니다. 설계는 이렇습니다. Workato On-Premise Agent를 사내망 안에 설치해서 SAP RFC 호출을 직접 하게 합니다. Workato MCP Server는 이 Agent를 통해 SAP 데이터를 AI 툴로 노출합니다. SAP은 외부에 열리지 않고, Agent가 안전하게 브릿지하는 구조입니다.
>
> 거버넌스 관점에서 세 가지가 중요합니다. 어떤 RFC 함수를 AI가 호출할 수 있는지 허용 목록을 명시적으로 정의하는 것, 모든 호출이 감사 로그에 남는 것, SAP 데이터 쓰기 같은 액션은 사람 승인이 필요한지 자동으로 해도 되는지 구분하는 것입니다. SAP 데이터는 downstream 영향이 크기 때문에 특히 중요합니다."

## Q-기술2. VUA가 왜 중요한지, IT 보안팀 설득에 어떻게 활용할 수 있나요?

> "VUA, Verified User Access는 Workato 특허 기술입니다. 공유 서비스 계정이나 공유 토큰이 아니라, AI가 항상 요청자 본인의 권한으로 시스템에 접근하는 구조입니다.
>
> IT 보안팀이 AI 도입을 막는 이유는 대부분 하나입니다. 'AI가 내 권한을 넘어서 뭔가 할 수 있다'는 두려움입니다. POC에서 공유 크레덴셜을 쓰면 이 우려가 현실이 됩니다.
>
> VUA를 보안팀에게 설명할 때는 이렇게 접근합니다. '새로운 보안 규칙을 만드는 게 아닙니다. 지금 회사에 있는 접근 제어 정책을 AI에도 그대로 적용하는 겁니다. 인턴은 인턴 권한만, 재무팀장은 재무팀장 권한만. AI가 사람처럼 권한을 갖는 구조입니다.' 이 설명이면 보안팀이 yes를 할 수 있는 근거가 생깁니다."
